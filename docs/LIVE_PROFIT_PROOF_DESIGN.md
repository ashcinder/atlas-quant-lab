# 真实成交来源与实盘收益证明协议设计 v1

状态：设计规范，未实现此 guest、数据认证服务或实盘验收。当前回测 receipt 和合约不能标成实盘收益证明。系统保留中心化网站、数据库、交易所接入和运维；不要求完全去中心化。

## 1. 首版产品边界

仅支持 Binance Spot 单独专用账户、BTC/USDT、无杠杆，无借贷、理财、质押、提现费抵扣等旁路资产变动；手续费资产限定 BTC 或 USDT，关闭 BNB 抵扣。账户不允许同时运行其他策略或人工交易。Binance Spot Testnet 独立命名，不与主网业绩合并。OKX、券商、衍生品、跨币种汇率和多策略账户另立 profile。

一次报告覆盖明确 UTC 区间 [t0,t1)，绑定同一账户、同一策略版本、同一执行授权和公开收益口径。ZKP证明的是认证输入下的账本计算及相应约束，不保证交易所诚实、不保证策略盈利，也不证明现实世界不存在未纳入监控的账户。

## 2. 信任边界和角色

| 角色 | 可见内容 / 职责 | 不能获得的权力 |
|---|---|---|
| 作者 | 源码、策略密钥、认可的执行镜像 | 不能自行签出“交易所成交”证据 |
| 用户 | 自己账户与订单、授权范围、报告 | 无需读取策略源码 |
| 平台 | 密文、调度、订阅、公开证明、运营 | 不能通过数据库字段升级证明等级 |
| TEE执行器 | 解密策略、受限交易权限、状态和模型 | 不能提现，不能导出源码或绕过密钥政策 |
| 数据认证 verifier / notary | 验证TLS会话、域名、时间/挑战及规定的字段 | 不持有账户交易或提现权限；其信任根需要公开固定 |
| ZK prover | 认证会话证据与私有账本；若放在普通主机则该主机能看到输入 | 不可把未认证字段当成交来源 |
| 链上验证器 | 证明、公开摘要、登记身份及最终状态 | 不代替TLS来源或交易所经济保证 |

采用 zkTLS / MPC-TLS 时必须选择具体版本、服务端身份验证方式、信任模型和可递归验证方式后再实现。不能把“使用TLS”或平台自己签名等同于第三方可验证来源。若选择 notary 签名供 guest 验证，应清楚标记为“信任该 notary 的来源认证＋ZK计算”，而不是无信任来源证明。若要求平台运营者不能伪造，notary不能仅由同一个平台控制。

## 3. 账户和策略登记

建立私有 `account_binding`：交易所、网络、不可变账户身份、API权限与专用账户声明。公开 `account_commitment = H(domain, venue, network, immutable_account_id, random_salt)`。API key不是账户永久身份，更换key必须通过认证证明绑定到原账户；若交易所接口不能稳定证明账户身份，暂停发行可验证报告。

策略登记包含 `strategy_commitment`、版本、执行程序/镜像标识、输入规格、风险限制、费用口径和模型承诺。源码明文不上链、不写普通数据库。作者用认可的执行镜像远程证明控制解密密钥释放；这个步骤是TEE安全条件，不由本账本ZKP替代。

用户授权 `mandate` 绑定账户、策略版本、交易对、最大仓位、订单频率和有效期。授权应签名并含 nonce、链ID及登记合约地址，避免跨链/跨合约重放。

## 4. 认证采集和完整性

每次采集必须验证域名、证书链、HTTP方法、规范化路径、查询参数、响应码、请求挑战、响应内容完整性。认证账户、网络和时间范围须贯穿每页，不能只证明盈利字段或截图。

数据集合包括：期初余额、期末余额、所有订单及成交、充值、提现、内部划转、其他账户调整事件、手续费、估值快照和策略信号。必须覆盖该账户所有会改变权益的事件类型；“未提供某种事件”不能当成没有这种事件。

分页按API实际规范实现：排序键、去重键、起止边界、页长、下一页条件、空终止页/结束游标全部验证。必须保存认证请求和响应的关联。若接口只给“最近N笔”且不能可靠覆盖整个区间，报告状态为 `incomplete`，不能生成完整收益声明。

WebSocket 用于低延迟，不单独承担完整性保证。断线重连后由认证REST回补并按交易所唯一ID去重；补齐前不封账。交易所一致性延迟需要封账等待窗口，并再次查询边界，避免迟到成交遗漏。

专用账户约束减少歧义，但不能自动证明没有人工下单。对每笔已认证成交追溯订单ID和授权信号；出现无法归属的订单，整期标记为 `unattributed_activity`，不给出“完全由该策略产生”的结论。

## 5. 来源证据结构

每个认证包包含 `protocol_version, verifier_id, server_name, certificate_binding, request_commitment, response_commitment, session_time, challenge, account_commitment, venue, network, endpoint_kind, range, pagination_link, transcript_proof`。

guest 必须验证该证据的密码学有效性，或验证明确列入可信名单的 notary 对规范化声明的签名。若直接递归验证原始TLS证明，需要证明系统间兼容性设计与性能测试。不要在guest外验证后只传入一个 `valid=true`。

密钥、Authorization头和个人身份可作为私有输入隐藏；解析必须检查规范化、重复JSON字段、数值精度、Unicode/转义、字段遗漏和意外响应类型。认证的原始字节和计算使用的数值之间不能存在未验证转换。

## 6. 账本和收益算法

所有资产使用规定最小单位整数，限制总值和乘法中间值，检查溢出；禁止使用客户端浮点数作为资产事实。BTC/USDT数量、价格和手续费按profile固定精度解析，超精度输入拒绝。

逐笔更新：买入减少USDT、增加BTC；卖出减少BTC、增加USDT；手续费按实际收费资产扣除。部分成交逐笔计入，撤销未成交部分不当成交。订单的累计量与逐笔成交总量应核对，不能同时重复计账。

账本重放的期末余额必须与认证期末余额在规定精度内一致，冻结余额与可用余额分开处理。差异不是收益误差容忍项：无法解释即 `reconciliation_failed`。同资产内部转移在适当账户范围内抵消，范围外资金变动作为外部资金流处理。

净利润定义为：`期末权益 - 期初权益 - 净外部流入`。这个金额指标不等于收益率。权益按明确的认证估值时刻与价格来源换算，不能用事后最高价估值。测试币余额也必须标为测试网权益。

首版无外部资金流时，收益率为 `(E1-E0)/E0`，E0必须大于0。若支持期间资金流，采用现金流前后分段估值的时间加权收益TWR：每段收益相乘后减1。必须获得每次流入/流出前后的认证估值；缺少时不能偷换成简单收益率。可另列 Modified Dietz 作为明确标注的近似指标，但不能使用同一精确TWR标签。

最大回撤来自按固定频率、固定估值口径得到的完整净值序列；对含资金流账户使用单位化净值。公开采样曲线不证明更细粒度的最大回撤。频率必须写入公开statement，不能宣称未观测期间无更大回撤。手续费已经体现在余额，不可再重复扣除。

## 7. 证明策略执行与证明账本的组合

来源证明回答“数据来自哪里”；账本证明回答“基于这些完整数据怎样计算”；策略执行证明回答“订单意图是否由指定策略产生”。三者分开验收，再通过公共承诺组合。

每个信号绑定 `run_id, strategy_commitment, account_commitment, sequence, previous_state_root, market_input_root, target/order_intent, timestamp/expiry, mandate_hash`。执行器签名不是ZKP；若使用TEE签名必须验证其远程证明和认可镜像。如果使用zkVM执行证明，必须在guest中生成信号承诺并验证前后状态连续性。

订单提交结果经认证绑定交易所订单ID、客户端订单ID及账户。只比对客户端订单ID字符串不够，因为作者也可能编造它。成交证明再绑定订单ID和真实成交ID。不得强行证明成交价等于策略目标价；部分成交、滑点、拒单是交易所结果，按真实结果更新状态。

顺序需要证明前后状态连续、未重复处理事件和完整期间覆盖。每期引用上一期 receipt/journal 摘要，登记合约只允许接受该账户/策略链的下一个序号，不能挑选盈利子区间覆盖亏损区间。允许中断，但必须公开中断，不能补造连续记录。

## 8. 新 guest 的公开输出与链上应用

实盘必须创建新 profile/image，不能复用 `atlas_program_backtest_risc0_v2`。建议输出采用固定版本 ABI 编码，便于合约解析，而不是任意JSON字符串。

公开字段至少：`schema_version, chain_id, registry_address, venue, network, account_commitment, strategy_commitment, mandate_hash, report_kind, period_start/end, sequence, previous_journal_digest, authenticated_data_root, execution_root, opening/closing_equity, net_external_flow, net_profit, return_method/value, valuation_policy_hash, drawdown_frequency/value, order/fill_count, completeness_policy_hash, source_verifier_policy_hash, nullifier`。

合约验证实际Groth16证明、固定image ID及journal摘要，然后解析该ABI结构，检查域隔离、账户登记、策略版本、网络、连续序号、上一期摘要和nullifier唯一。数据根或数字由交易发起人另传时，必须与journal字段相等。禁止管理员绕过证明写入“已验证”状态。

当前 `AtlasReceiptRegistry` 只验证固定guest的原始journal并登记digest，没有解析实盘结构，不能当作已经实现此状态机。升级应部署新合约/profile并保留旧证明可验证性；紧急暂停可以阻止新提交，不能把无效证明改成有效。

## 9. 状态机与失败策略

`registered → authorized → collecting → reconciling → proving → locally_verified → submitted → confirmed`。

独立失败状态：来源失效、账户不一致、分页不完整、时间边界缺失、余额无法对账、策略无法归属、价格缺失、证明失败、交易回滚、链重组。失败状态不能回退成普通平台签名并保留“ZKP收益”标签。链上确认还需规定确认深度/最终性，RPC成功回执不等于不可重组。

所有证明输入、认证包及程序版本应内容寻址存储，公开足以独立复核的材料。私有原始数据加密保存且生命周期明确；保密托管依赖TEE，ZKP不会隐藏普通证明主机的内存。

## 10. 验收清单

1. 使用真实Testnet账户建立期初余额，完成买入、部分成交、卖出、手续费、撤单，认证获取全部响应。
2. 真实证明能被独立验证器及链上合约接受，公开结果与用户账户对账一致。
3. 修改成交价/数量/域名/账户/网络/时间/认证签名任一项必须失败。
4. 漏一页、漏亏损单、漏手续费、重复成交、充值伪装利润、错估值、期间截断必须失败或明确拒绝完整性声明。
5. 不可归属的人工订单必须取消纯策略收益声明；不能根据备注强行归属。
6. 错image、错journal、跨链/跨合约提交、重复nullifier、跳序/分叉、无效上一期必须被合约拒绝。
7. API断线、迟到成交、交易所数据重置、后台重启、TEE重新证明、证明超时和链重组测试。
8. 测试报告明确标记Testnet；迁移主网只使用只读验证/授权范围内的交易，另行验收。

## 11. 实施前必须冻结的选择

确认具体zkTLS协议/版本及运行方、接口是否支持所需证明与完整分页、账号认证字段、notary信任政策、证明成本和时延、支持资产/事件类型、TEE镜像和密钥控制、合约最终性策略。上述任何一项无法满足时，应缩小声明范围，不伪造“完整实盘收益证明”。
