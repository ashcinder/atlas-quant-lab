# 风格监管：持仓与动态名单核验

入口：登录后选择「风格监管」，或访问 `#style-review`。

## 演示步骤

1. 点击「载入75% → 85%示例」。所有证券为合成数据，不对应真实基金。
2. 在「规则与数据」查看合同示例、100万元非现金资产、三个持仓和两版名单。
3. 点击「核验并保存快照」。工作台显示新版比例85%、覆盖率100%、一只入库证券缺少依据。
4. 打开「变化分析」。同一持仓按V1为75%，按V2为85%；公司B贡献10个百分点。
5. 打开「历史与复核」，追加“待补材料”等说明。原报告不变。
6. 导出JSON复核包，在「复核包验证」重新导入。检查摘要和计算是否一致。
7. 修改JSON中的结果再验证，观察不一致。注意：攻击者同时修改数据、结果和摘要仍可能通过；本功能不是签名认证。

## 数据录入

支持UTF-8 CSV（可有BOM）、标准CSV引号转义，也可直接编辑文本。

- 持仓表头：`code,name,value`，证券代码唯一，value为统一币种的非负市值，最多6位小数。
- 名单表头：`code,name,basis`，证券代码唯一，basis为人工提供的入库依据或材料位置。
- 每份最多5000行。当前不支持Excel直接导入、空头、衍生品风险敞口或跨币种自动换算。
- 同一证券的多笔持仓应先汇总。完整持仓须包含全部非现金资产，且合计等于分母。
- 不完整持仓以已知主题资产计算下界，将未覆盖资产全部假设为主题资产计算上界。
- 上界低于阈值时标记比例偏离；下界达到阈值时标记本项比例达标；其余为证据不足。
- “在库”仅代表名单成员关系，不代表其符合合同资格。缺少入库依据单独列示。
- 默认80%是可编辑的产品参数，不是对所有公募基金统一适用的法规判定。

## 四项能力

- 复核效率：一张持仓表同时展示新旧成员关系、入库依据和逐项名单影响。
- 原因解释：固定同一持仓，仅替换名单；不把名单影响混称交易影响或投资收益。
- 历史追溯：报告固定保存全部输入、版本、生效日及服务器接收时间；备注只追加。
- 可移交复算：JSON复核包包含输入、结果及摘要，接收方登录后可重算；导入验证不落库。

当前只保存提交核验时的风格库/规则快照，不是完整的风格库审批和定时发布系统。
同一账号、基金、版本号的内容不可重写；按语义排序后的名单计算版本指纹。
新版本可以复制已有报告，但必须填写新的版本编号。数据库管理员仍可修改底层数据，
不可覆盖是应用级约束，不等于外部不可篡改存证。

## 存储、权限与部署

后端沿用现有登录与同源检查。新数据存放在 `ATLAS_DATA_DIR/style_review.db`，
按当前登录账号隔离。没有对外分享接口、自动报送接口或机构身份切换。
报告不含认证密钥；导出包含持仓明细和人工填入的来源信息，分享前须由用户确认接收方授权。
复核记录的actor来自登录账号，不接受客户端指定身份。

SQLite文件应与其他应用数据一起备份。正常前后端构建部署后生效，无需新增依赖或外部服务。
新数据库在首次请求时创建，不修改原有数据库表。

## API

- `POST /api/v1/style-review/reports`：验证输入并追加不可覆盖的报告快照。
- `GET /api/v1/style-review/reports`：当前账号最近200份报告摘要。
- `GET /api/v1/style-review/reports/{id}`：读取快照及追加的复核记录。
- `POST /api/v1/style-review/reports/{id}/notes`：追加说明和处理状态。
- `POST /api/v1/style-review/verify`：验证包内SHA256并以style-review-v1重算。

摘要方案为typed-json-ieee754-v1：所有值显式标记类型，对象键排序；数字按IEEE754双精度大端字节编码（零规范为正零），再以紧凑UTF-8 JSON计算SHA256。这样浏览器将85.0导出为85时仍保持一致。
摘要覆盖payload，不包含导出时附带的notes。摘要不能认证来源、机构或签发时间。
