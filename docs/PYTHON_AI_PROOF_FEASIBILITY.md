# Python／AI执行证明可行性评估

本轮仅评估，不扩展Python解释器、编译器或AI执行实现。

## 判断

现有项目可作为可验证策略平台的基础，但当前证明环境不能证明任意Python/AI。可交付目标应写成“明确版本、依赖、输入与资源上限内的执行证明”，不承诺无限制程序。

| 使用方式 | 当前可行性 | 需补齐的工作 |
|---|---|---|
| AI辅助写出受支持整数策略 | 已有可用基础 | AI产生的代码仍需审核/编译/测试；证明覆盖编译程序执行，不证明AI生成过程 |
| 现有严格Python子集 | 已验收编译后程序的回测证明 | 编译器是可信转换组件；源码与编译结果等价性未纳入ZKP |
| 固定Python解释器和纯Python库 | 技术上可研究实现 | 将解释器/依赖移植或编译进guest，确定系统调用、确定性、资源上限与新image；先做代表性策略性能原型 |
| NumPy/Pandas及原生扩展 | 需要逐项适配 | C扩展、浮点、线程、动态加载和平台差异可能影响移植与成本，不能默认与现有后端等价 |
| 固定小模型的整数推理 | 有可实施方向 | 固定权重承诺、张量形状、量化/激活/舍入、输入预处理，在zkVM或专用zkML证明中执行并绑定交易决策 |
| 运行中调用外部LLM API | 不能直接证明其内部推理 | 认证API响应只能证明服务商返回某内容；若需要推理证明，服务商必须提供可验证推理，或自行托管可验证模型 |
| 任意联网/随机/无限循环Python | 不适合作为无边界交付承诺 | 网络和随机源须认证并固定输入，循环/内存/指令须限额，失败不能生成成功执行证明 |

## 当前工程的有利基础

固定RISC Zero profile、私有程序承诺、真实receipt验证、重放防护、报告绑定、策略版本与运行记录，以及本轮完成的Groth16转换和链上验证。现有编译子集可以继续承载轻量规则策略，而无需暴露参数。

## 不能复用为已完成能力的部分

Python后台运行成功、TEE镜像签名、AI接口返回结果、界面显示多种语言，都不等于相应程序已经进入ZKP。当前策略zkVM没有网络、完整Python解释器或模型推理计算；现有链上合约也只认可固定回测guest。

## 建议的分阶段验收目标

第一阶段保留规则策略/整数子集，AI只辅助开发。明确证明编译后的程序，而不是营销为任意Python。

第二阶段选择固定Python解释器或固定模型中的一条路线，做独立性能原型：使用真实代表性策略/模型，在目标机器测量执行时间、证明时间、峰值内存、证明大小及链上成本。没有这些实测，不承诺秒级/高频每笔证明，也不估算虚假的完成百分比。

第三阶段将实时执行与批次证明分开：真实交易按风险约束运行，按时间/事件批次证明，公开证明延迟和失败状态。批量证明必须连续绑定输入、状态和账本；不能只挑盈利批次。

第四阶段再接入认证成交来源与实盘账本新profile。TEE用于保护源码和运行中秘密，ZKP用于计算验证，来源认证用于证明输入来源，三者各自验收。

因此，核心目标可以在限定规格后实现；当前项目尚不能直接交付任意Python或外部AI内部推理的证明。租用TEE只解决部分保密执行前提，不会自动完成这些证明协议。
